# Hermes Agent + Hermes Studio 日志与故障排查

## 1. 日志入口

安装并启动应用后，日志入口位于应用中心的应用卡片菜单；也可以在家庭局域网浏览器直接打开：

- Hermes Agent：`http://NAS_IP:8643/`
- Hermes Studio：`http://NAS_IP:8649/`

日志页面只绑定在 NAS 上，适合本项目的家庭局域网使用范围。页面可以选择日志文件、刷新最近内容，并导出完整日志包。

## 2. 日志文件

日志位于对应应用的 `TRIM_PKGVAR/logs/`：

| 文件 | 内容 |
| --- | --- |
| `install.log` | 安装、升级、配置回调记录 |
| `app.log` | 应用启动、停止、路径和端口记录 |
| `gateway.log` | Hermes Agent Gateway 标准输出和错误 |
| `browser.log` | 浏览器相关输出预留日志 |
| `studio.log` | Hermes Studio WebUI 标准输出和错误 |
| `log-viewer.log` | 日志页面本身的访问和错误 |

Agent 主要查看 `install.log`、`app.log`、`gateway.log`；Studio 主要查看 `install.log`、`app.log`、`studio.log`。

## 3. 安装失败时的判断顺序

如果应用中心提示“解压 app.tgz 失败”，这通常发生在应用生命周期脚本执行之前，因此设备上可能还没有 `install.log`。`0.1.7` 起，Hermes Agent 使用小型 `app.tgz` 安装层：fnOS 只解压日志服务、界面、静态解包工具和一个运行时载荷文件；完整 Python/Chromium 文件树在首次启动时由 NAS 本地离线展开。运行脚本按 fnOS 的实际解压目录读取这些文件，并由 fnOS 直接守护 Gateway。

从 `0.1.8` 起，Studio 与 Agent 的安装回调都采用相同的诊断机制：即使回调很早失败，也会尝试同时写入 fnOS 临时日志、应用运行日志和共享目录诊断文件。Studio 的共享目录诊断文件名为 `HermesStudio-install-diagnostic.log`，Agent 的为 `HermesAgent-install-diagnostic.log`。因此不再只出现“执行脚本出错且原因未知”。

`0.1.9` 修复了部分 fnOS 上不存在 `/var/apps/HermesAgent/share/data` 的情况。Studio 会通过 Agent 的受控路径元数据取得实际 Hermes 数据目录；Agent 的共享启动器也会定位自身运行时，而不会错误使用 Studio 的运行时目录。Studio 改用前台模式运行，使 fnOS 能准确管理和判断其服务状态。

`0.1.10` 进一步按 fnOS 的实际卷目录推导 Agent 路径：从 `/volN/@appcenter/HermesStudio` 找到同卷的 `/volN/@appcenter/HermesAgent` 和 `/volN/@appshare/HermesAgent/data`。因此即使 `/var/apps` 映射与 `/usr/local` 启动器链接不可用，Studio 仍能连接已运行的 Agent。

`0.1.11` 让 Studio 与 Agent 使用同一个 fnOS 专用运行用户 `hermesagent`。这是因为 Hermes Studio 的上游初始化会向 Agent 的 `skills/`、`config.yaml` 和 MCP 配置写入内容；在部分 fnOS 1.2 设备上，Agent 后续创建的子目录权限不会继承 `config/resource` 中的跨用户 ACL。Studio 启动前会记录 `id` 和关键目录权限，并在无读写执行权限时直接给出明确错误。

`0.1.12` 进一步增加了主脚本入口和 `common` 初始化阶段的最早期诊断。若旧版升级留下的 Studio `@appdata` 目录不可写，Studio 会将自己的日志、PID、临时文件和 WebUI 状态放在 Agent 数据目录下的 `.hermes-studio`，不改变 Agent 的工作目录和配置。若仍无法初始化，会将原因写入 fnOS 提供的 `TRIM_TEMP_LOGFILE`。

`0.1.13` 会把 Studio 启动的 Agent Bridge 子进程输出保存到 `agent-bridge.log`，并在主启动脚本中等待 Studio `/health` 返回成功后再报告“已启动”。因此 fnOS 不会在 WebUI 尚未就绪时过早打开窗口；若 Bridge 仍无法启动，可直接查看该日志中的 Python/import/权限错误。

`0.1.14` 修复了 Bridge 找不到 Agent 运行时的问题。Agent 的 `run_agent.py` 安装在内置 Python 的 `runtime/python/lib/python3.11/site-packages/` 中，Studio 启动时会自动检测该文件并导出 `HERMES_AGENT_ROOT`。如果 Bridge 仍失败，请查看 `agent-bridge.log` 中的完整 Python 错误，而不是只根据 Studio 页面是否能打开判断。

`0.1.15` 修复了两个由环境变量继承造成的问题：`HERMES_AGENT_BRIDGE_PYTHON` 现在会真正导出给 Node/WebUI，避免上游误把 Agent shell 启动器的 `#!/bin/sh` 当成 Python，进而出现 `/bin/sh ... import: not found`；同时 Studio 会继承 Agent 的 `WORKSPACE_DIR`，旧配置没有工作区时则在 Agent 数据目录创建默认工作区。Studio 入口改为 `url`，由 fnOS 使用完整浏览器打开，避免应用内 iframe 在服务已监听时仍显示连接拒绝。

`0.1.16` 修复插件列表为空且报 `Unexpected end of JSON input` 的问题。插件发现命令必须把 JSON 写到标准输出供 WebUI 解析；Studio 的诊断包装器现在只把长期 Bridge 的输出写入 `agent-bridge.log`，对插件发现保留标准输出，同时继续记录标准错误。该修复只涉及 Studio，不需要重新安装或编译 Hermes Agent。

Actions 构建阶段会执行以下检查：

1. 解包外层 FPK。
2. 查找内部 `app.tgz`。
3. 执行 `gzip -t`。
4. 执行 `tar -tzf`。
5. 检查是否包含绝对路径或 `..` 路径。
6. 使用随 Agent 打包的 BusyBox 实际展开运行时载荷，并校验 Python、启动器和版本标记。

检查结果随 Release 发布为 `fpk-payload-check.log`。安装失败时，请先确认下载的是同一 Release 的两个 FPK，并重新下载后校验 `SHA256SUMS`。

## 4. Studio 依赖关系

必须先安装并启动 `HermesAgent`，再安装 `HermesStudio`。当前安装兼容性修复版本为：

- Agent：`0.1.9`
- Studio：`0.1.16`
- Studio 的依赖条件：`HermesAgent>0.1.0`

旧版 Studio 使用同版本 `0.1.0` 的 Agent 时，版本条件无法满足，这是旧版依赖声明的问题。请先安装 Agent `v0.1.9`，再安装 Studio `v0.1.16`。升级 Studio 时建议先停止并卸载旧 Studio，再安装新版 Studio；Agent 不需要重新编译或升级。

## 5. 提交排查信息

出现运行问题时，优先导出对应应用的日志包，并同时提供：

- fnOS 版本和设备架构。
- 使用的 FPK 文件名。
- `SHA256SUMS` 中对应的校验值。
- 操作步骤和准确报错文本。
- Agent 和 Studio 的状态。

日志中可能包含上游服务错误信息，但打包层不会主动记录 API Key 等配置值。发送日志前仍应自行检查并删除个人账号、Cookie 或其他敏感信息。
